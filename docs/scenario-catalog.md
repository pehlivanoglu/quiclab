# Scenario catalog

Generated by `scripts/scenario_catalog.py` from the configuration files, the planners and the run folders (read-only). Do not edit by hand; rerun the script after a change.

Contents: 0 testbed, 1 video and sender, 2 topologies (links, shaping stages, capacities, delays, queue limits, RTTs, designed load), 3 scenarios and congestion events, 4 AQMs, 5 measured calm load and video share, 6 campaign matrix.

## 0. Testbed in one page

- Emulation: Mininet. Nodes: one publisher (`pub`, qvideo-server), routers (queues), switches (fan-out only), clients (qvideo-client), plus iperf3 / PPBP endpoints for cross traffic on named routes. Link changes (capacity, delay, jitter, loss, AQM) are applied live with `tc ... change` at the planned times; the applied time of every event is in the run's `events.csv`.
- Every topology has the control client `sub-ctrl` (2500 kb/s) on its own router egress next to the publisher: it never shares a congested queue and must never be grouped.
- Router metrics: every router egress every 25 ms (queue packets and bytes, transmitted bytes, drops, ECN marks); split, tree8 and uneven also record the queue every 5 ms; fq_codel / cake add per-client class counters (since 2026-11-11).
- Truths used in the reports: **GT1** = CoDel-style standing queue on a router egress (target 5 ms, interval 150 ms); **GT2** = demand >= capacity; **GT3** = the client's own OWD + loss episodes with a queue on its path. Grouping truth = the topology's leaf sets (clients behind the same leaf egress). The detector is the frozen Shadow v2 on OWD ticks (v2-owd); grouping methods are ECG v1.2 (onset co-occurrence, delta 150 ms) and the template-based h3 of steps 3 / 4.
- Every run folder holds the resolved `topology.yaml` and `scenario.yaml` (every event with its time), `grouping/plan.json` (campaign, type, AQM, rep = seed, phase, keyframe phases, duration), `grouping/windows.json` (stimulus windows and expected clients), `grouping/keyframe-spread.json` (sync-era runs), sender / client logs and router metrics.

## 1. Video and sender

- qvideo-server over mvfst QUIC, congestion control **bbr**, pacing on (per connection); one QUIC connection per client, one unidirectional stream per GOP.
- Ladder [500, 1000, 2500, 5000, 8000, 12000] kb/s; each client takes one fixed rendition (no ABR).
- **30 fps, GOP 1000 ms = 30 frames, no B-frames, I/P size ratio 4**, per-frame lognormal size noise sigma 0.2 (mean kept), frame header 40 B, seed 1 (every client of one rendition gets byte-identical frame sizes).
- Frame sizes: GOP bytes = rate / 8 x 1 s; P mean = GOP / (I/P + frames - 1) = GOP / 33; I mean = 4 x P = GOP x 4/33 (~12 % of a second of data).

| rate kb/s | GOP kB | P frame kB | keyframe kB |
|---|---|---|---|
| 500 | 62.5 | 1.9 | 7.6 |
| 1000 | 125.0 | 3.8 | 15.2 |
| 2500 | 312.5 | 9.5 | 37.9 |
| 5000 | 625.0 | 18.9 | 75.8 |
| 8000 | 1000.0 | 30.3 | 121.2 |
| 12000 | 1500.0 | 45.5 | 181.8 |

- Schedule: frame k is due at start + phase + k / fps, start shared by all clients; keyframes at k % 30 == 0. Frames are handed to QUIC whole when due; an application queue of at most 1000 ms of media sits in front of QUIC (GOP-aware head drop) and holds frames while QUIC's unsent bytes exceed the congestion window.
- Client: playback buffer 600 ms, QUIC PING every 50 ms (keeps ACK receive timestamps flowing), stats every 100 ms. Sender logs per client: frames, sent packets, ACKs (RTT, cwnd, BBR state, OWD from ACK receive timestamps), CC state every 50 ms, OWD per 5 ms send bin.
- Wire overhead used for load sizing: x1.03 of the video rate (det_matrix.WIRE_OVERHEAD).
- Keyframe phases: **stag** = the topology files' phase_ms (runs before 2026-11-13); **sync** = every client phase 0 (grouping_campaign --phase sync, default since 2026-11-13).

## 2. Topologies

Shaping (quiclab/orchestrator/shaping.py, mininet_backend.initial_shaping_commands): **every link direction** gets an htb rate limit (the link's bandwidth, else the scenario's link_defaults, 100 Mb/s here); a netem stage when the direction has delay / jitter / loss; an **AQM qdisc only on router egresses** (the router's AQM and queue limit; per-egress overrides possible). Switches, the publisher and the clients have no AQM. Congestion happens on router egresses only. Queue delay at the limit = limit x 1500 B / capacity.

## 5. Calm load per bottleneck (measured)

Load = egress transmitted bytes / capacity over calm time (outside stimulus windows +- 1 s, after warm-up). Video share = bytes the publisher sent to the clients behind the egress / bytes the egress transmitted, same time (can be slightly above 1: packets still queued or lost). Designed value 0.65 unless the scenario changes it (calm030 / calm090 / calmcbr090, bw*, K6R root). Only egresses with load >= 0.02 are listed; sub-ctrl's own egress included.

Reading the video share: the publisher's sent.csv counts QUIC packet bytes while the router counts IP / UDP headers too, so an egress that carries only our video shows ~0.96. Values clearly below that are cross traffic: calmcbr090 (constant-rate UDP to load 0.9) and ppbp (PPBP UDP, total load ~0.95). Burst-type cross traffic (burstudp, tcp*, N3) runs only inside stimulus windows, which are excluded here. The ramp type keeps sub-1 steps (load 0.9-0.95) outside its windows, hence its higher calm load. sub-ctrl's egress carries only its 2500 kb/s stream (load ~0.05 of 50 Mb/s).
